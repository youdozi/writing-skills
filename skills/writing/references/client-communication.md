# 개발 프로젝트 고객 커뮤니케이션

개발자가 고객에게 보낼 메일·메신저·진행 보고·요구사항 확인·변경 협의·장애 안내·검수/인수인계 문서를 작성·퇴고할 때 적용한다. ‘시니어’는 과장된 권위나 연차 자랑이 아니라 판단 근거·영향·실행 가능한 다음 단계를 책임 있게 전달하는 기준이다. 없는 경력·담당 권한·조사 결과를 만들어 설득하지 않는다.

## 고객이 판단할 내용부터

고객이 알아야 할 현황·결론·협의 요청을 먼저 밝히고 필요한 이유를 붙인다. 채널과 요청 범위에 맞춰 핵심을 좁힌다. 기술 세부는 고객의 일정·사용 방식·비용·운영에 미치는 영향을 설명하는 데 필요한 만큼 쓴다. 기술을 모르는 사람으로 낮춰 보거나 모든 전문용어를 장황하게 풀지 않는다. 기술 고객이면 주어진 수준에 맞춰 근거·제약을 유지한다.

현재 요청과 원자료에서 확인된 사실, 해석·추정, 제안, 합의·승인된 사항을 구별한다. 고객의 목적을 확인한 범위를 넘어 재해석하거나 회의 중 제안을 확정 요구사항으로 바꾸지 않는다. 불가능/가능을 단정할 근거가 부족하면 필요한 확인 범위와 그 이유를 밝힌다. 구현 방안·원인·비용·일정에 대한 전문 지식이 필요한 주장만 별도 검증하고, 단순 문구 교정을 기술 조사 전체로 확대하지 않는다.

읽은 고객이 ‘무엇이 달라졌는지, 내게 어떤 영향이 있는지, 무엇을 결정하거나 준비하면 되는지’를 알 수 있게 한다. 해당하지 않는 요소를 매번 표나 고정된 다섯 문단으로 붙이지 않는다. 정보 전달만 필요한 메시지에 불필요한 승인·답장을 요구하지 않는다.

## 일정·비용·변경 협의

- **요구사항 확인:** 요청한 기능과 해결하려는 일을 구별하고, 구현 범위를 바꾸는 모호함만 좁혀 묻는다. 결정이 필요한 항목에는 왜 답이 필요한지, 어떤 범위가 달라지는지 연결한다. 사소한 누락까지 질문 목록으로 되돌려 보내지 않는다.
- **견적·일정:** 확정 날짜/금액과 조건부 예상·계산 예시·미산정을 구별한다. 제공된 작업 범위, 공수 단위, 영업일/달력일, 세금·결제 조건을 보존한다. 의존 작업·고객 제공 자료·승인 전제를 해당 예상 가까이에 두고, 근거 없는 여유율·납기·무료 작업·인력 투입을 보태지 않는다. 정보가 없으면 산정 전 필요한 확인과 합의할 내용을 좁혀 쓴다.
- **변경 요청:** 현재 합의 범위와 추가 요청, 그에 따라 검토할 영향을 구별한다. 실제 가능한 대안이 있으면 효과·제약을 비교하고 권고와 근거를 제시한다. 모든 요청에 임의로 ‘일정 유지/범위 축소/추가 비용’ 세 안을 만들지 않는다. 제안한 비용·일정·범위를 고객 승인 전에 확정하거나, 기존 약속을 일방적으로 철회하지 않는다.
- **지연·진행 보고:** 완료·진행·막힌 항목과 납기에 미치는 영향을 구별한다. 늦어지는 사실을 기술 설명이나 모호한 ‘순조롭게 진행 중’으로 감추지 않는다. 이미 한 일과 앞으로 할 일, 확인된 의존성과 책임 추정을 구별한다. 고객에게 필요한 자료/선택이 있으면 구체적으로 요청하고 원인 규명 전 상대의 탓으로 단정하지 않는다.

내가 통제할 수 있는 다음 조치와 다른 사람의 승인·외부 결과를 분리한다. 새 납기·회신 기한·추가 비용·무상 대응·SLA·인력 배정을 임의 약속하지 않는다. 확인된 다음 안내 시점이 있으면 지키고, 복구 시각을 모른다는 이유로 약속된 상황 공유까지 생략하지 않는다. 시점이 주어지지 않으면 허구의 시각을 만들기보다 확인 후 안내할 범위를 말하거나 꼭 필요한 확인만 받는다.

## 장애·불만·이견 대응

발생한 불편이나 업무 영향을 확인된 범위에서 인정하고, 현재 상태·확인된 영향·진행 조치·다음 안내를 우선 전달한다. 적절한 사과는 할 수 있으나 사과만 반복하며 사실과 대안을 빼지 않는다. 차분하고 단정하게 쓰며 고객의 불만을 비합리적이라고 평가하거나 개발자가 우위에 있다는 말투로 반박하지 않는다.

일시 복구와 원인 확정, 영향 범위 조사와 데이터 무손실 확인, 조치 적용과 재발 방지 검증을 구별한다. 일부 관측만으로 ‘전체 정상’, ‘데이터 이상 없음’, ‘재발하지 않음’을 약속하지 않는다. 고객에게 불필요한 내부 책임 공방·비밀키·개인정보·원본 로그를 전달하지 말고 필요한 증상·영향·조치를 설명한다. 민감한 세부를 감추려고 알려진 영향까지 축소하지 않는다.

기술적 이견은 고객의 목적과 우려에 답하면서 판단 근거·한계·실제 대안을 전달한다. ‘원래 안 됩니다’, ‘간단한 작업이 아닙니다’만으로 끝내지 않는다. 반대로 상대를 안심시키려고 구현 가능성·해결 일정·품질을 보장하지 않는다. 제공된 권고를 존중하되 근거가 없는 제안을 전문 판단으로 확정하지 않는다.

## 회의 정리·검수·인수인계

합의·미결·제안·후속 조치를 구별하고 담당자·대상·기한은 정해진 범위만 쓴다. 회신이 없다는 것을 동의로 만들거나, 검토를 부탁한 안을 채택된 결정으로 기록하지 않는다. 기존 문구의 최소 교정에서는 합의 내용이나 기한을 새로 설계하지 않는다.

구현 완료·개발 측 확인·고객 검수·운영 배포·고객 인수를 같은 상태로 쓰지 않는다. 전달물과 버전·시험 범위·남은 이슈·확인이 필요한 항목은 자료에 있을 때 반영한다. 개발 서버 테스트만으로 운영 정상이나 고객 승인을 선언하지 않는다. 인수인계 문서 요청에는 실제 절차를 제공하되 검수 요청 메일에 불필요한 매뉴얼 전체를 넣지 않는다. 계약 효력·귀책·보상에 대한 법적 결론을 글쓰기만으로 새로 정하지 않는다.

## 채널·표현·최종 점검

고객에게 바로 보낼 수 있는 원고가 기본이다. 메일은 필요한 제목과 본문, 메신저는 짧은 상황·요청, 보고는 읽고 판단할 정보 중심으로 쓴다. 요청하지 않은 설득 전략·감정 분석·긴 검토표를 붙이지 않는다. 실제 전송은 별도 명시적 지시가 있을 때만 한다.

정중함을 위해 주체·결론을 흐리거나 ‘아마/일단/최대한’으로 모든 책임을 모호하게 하지 않는다. 요청한 단호함은 가능한 범위와 조건을 명확히 하는 방식으로 구현하고 비꼼·압박·불필요한 감정 강화를 더하지 않는다. 유머는 관계·상황에 맞을 때만 쓰며 장애·비용·갈등의 중요한 뜻을 가리지 않는다. 다른 언어에서도 원래의 확정 수준·예의·기한·범위를 유지하며 언어만으로 협상 문화를 단정하지 않는다.

보낸다는 관점에서 읽고 요청·자료와 대조해 새 약속·새 기술 결론·합의 상태 변경이 없는지 살핀다. 고객의 다음 행동이 필요하면 답할 항목이 구체적인지 확인한다. 검토에서는 사실·약속·조건·승인 상태 오류와 선택적인 말투 제안을 나눈다. 글쓰기 품질을 실제 고객 만족·수주·협상 성과의 증거로 바꾸지 않는다.
