# 다국어 기술 블로그 작성

한국어·영어·일본어 및 추가 언어의 요청을 공통 기준과 해당 언어 지침으로 처리한다. 평가한 언어·작업·분량을 넘어 품질이 검증됐다고 주장하지 않는다. 사용자나 프로젝트에서 지정한 용어와 문체가 아래 기본값보다 우선한다.

## 작업별 결정

| 요청 | 유지할 것 | 조정할 수 있는 것 |
| --- | --- | --- |
| 대상 언어로 새 글 작성 | 제공된 사실·관점·근거 | 대상 독자의 이해 순서와 문장 구성 |
| 번역 | 주장·경험·조건·정보 범위 | 어순·문장 분리·자연스러운 연결 |
| 현지화 | 기술적 의미·적용 범위 | 독자에게 필요한 배경 설명과 표현 |
| 퇴고 | 대상 언어·저자의 말투·관점 | 정확성에 영향을 주지 않는 문장과 흐름 |
| 언어 버전 동기화 | 원문의 최신 변경과 버전별 사실 일치 | 변경된 부분과 직접 영향을 받는 문장 |

대상 언어, 독자, 지역, 격식은 서로 다른 선택이다. 한 가지 정보로 나머지를 단정하지 않는다. 기존 대상 언어 초안을 퇴고할 때는 다른 언어로 바꾸지 않는다. 짧은 번역 요청에는 번역문을 먼저 제공하고 검토표나 용어집을 일률적으로 붙이지 않는다.

## 의미와 기술 정보 보존

- 원문과 결과물의 핵심 주장을 직접 대조한다. 부정과 '오직', '적어도', '모두' 같은 범위 표현, 전제·예외·가능성·의무·조치 상태를 확인한다. 관찰을 보장으로, 계획을 완료로, 'may'를 '반드시'로 바꾸지 않는다.
- 숫자만 아니라 무엇을 세는지와 어느 구간을 가리키는지도 대조한다. 원문에서 단위가 없는 '3회 허용'에 번역자가 '총 실행 3회' 같은 대상을 임의로 보충하지 않는다. '실행 사이'와 '재시도 사이', '전체 응답 시간'과 '응답 시간의 합'처럼 수치가 같아도 의미가 달라지는 표현을 확인한다.
- 저자의 경험과 시점, 측정 환경·표본·기간·지표·기준을 보존한다. 응답 시간 감소를 처리량 증가로 바꾸거나, 퍼센트포인트 차이를 상대 변화율과 혼동하지 않는다.
- 수치·부호·범위·단위·버전·날짜·시간대를 대조한다. 지역에 맞춘 표기를 사용해도 값은 유지한다. 단위 변환이나 시간대 변환은 요청 또는 독자의 필요가 있을 때만 하고 원래 값과의 대응을 분명히 한다.
- 원문에 오류·모순·해석 불가능한 표현이 있으면 번역 과정에서 조용히 교정하거나 더 확실한 사실로 만들지 않는다. 예를 들어 `10/11`의 날짜 순서나 명시되지 않은 시간대를 임의로 정하지 않는다. 문맥으로 확정할 수 없고 핵심 의미에 영향을 주면 질문하거나 문제 부분을 확인 사항으로 분리한다. 오류 수정까지 요청받았다면 수정 내용과 근거를 구분한다. 번역문만 요청한 경우에도 의미를 결정할 수 없는 핵심 모호함은 먼저 확인한다.
- 코드 식별자, 명령 옵션, 환경 변수, 경로, 설정 키, API 이름, 실제 로그와 출력은 원칙적으로 그대로 둔다. 설명용 주석·문자열을 번역해야 한다면 실행 의미와 테스트에 영향을 주는지 확인하고, 실제 실행 결과처럼 꾸미지 않는다.
- 링크 주소와 인용 범위를 보존한다. 원어 자료를 근거로 한 설명을 대상 언어로 옮겨도 대상 언어의 공식 번역이 존재하거나 그 번역을 확인했다고 암시하지 않는다. 인용문 자체를 번역할 때는 번역임을 알 수 있게 한다.
- 현지화로 배경 설명을 추가할 때는 필요 범위로 제한하고, 원문 사실과 구별한다. 원문의 조직·서비스·경험·수치를 현지의 다른 사례로 바꾸어 실제 경험처럼 서술하지 않는다.

## 용어와 문체

프로젝트에 용어집이 있으면 관련 항목을 읽고 적용한다. 요청에 용어 지정이 있으면 우선한다. 용어집이 없으면 필요한 용어만 내부적으로 정리하고, 반복 작업에서 재사용할 필요나 저장 요청이 있을 때 파일로 남긴다.

| 기록 항목 | 내용 |
| --- | --- |
| 개념 | 원어와 문맥상 의미 |
| 언어별 표기 | 요청한 언어의 권장 표현과 첫 등장 표기 |
| 유지할 명칭 | 공식 제품명·API·코드 식별자 |
| 문맥별 예외 | 같은 단어라도 번역을 구분해야 하는 경우 |

원어 병기는 독자가 자료를 찾거나 개념을 구분하는 데 유용할 때 사용한다. 모든 용어를 반복 병기하지 않는다. 공식 명칭은 확인된 표기를 사용하고, 확인되지 않은 번역을 공식 명칭처럼 소개하지 않는다.

아래 항목은 언어별 교정 점검 사항이며 독자의 국적이나 문화적 성향에 대한 규칙이 아니다. 구체적인 글의 구성과 근거 제시는 [원문 사례 분석](blog-patterns.md)을 참고한다.

- **한국어:** 조사의 연결과 번역투를 다듬고 문서에서 선택한 기술 용어와 종결체를 일관되게 쓴다. 원문에서 중요한 행위 주체를 생략해 책임이나 조건이 달라지지 않게 한다.
- **영어:** 대명사와 수식어가 가리키는 대상을 분명히 한다. 주어·수·시제·관사와 연결을 점검하되 원문의 불확실성과 저자의 말투를 유지한다. 길이만 줄이기 위해 조건을 빼지 않는다.
- **일본어:** 기존 글의 敬体(です・ます) 또는 常体(だ・である)를 유지하고 혼용을 점검한다. 제품명과 식별자는 보존하고 기술 용어의 가타카나·한자·원어 표기를 일관되게 쓴다. 부정·가능·조건의 수식 범위가 원문과 같은지 확인한다. 문체 지정이 없는 새 설명문은 です・ます체를 출발점으로 삼되 사용자의 문체를 우선한다.

언어마다 특정 문장 길이·논리 구조·독자 성향이 고정돼 있다고 가정하지 않는다. 판단하기 어려운 표현은 과도하게 의역하지 않고, 그 표현이 핵심 의미에 영향을 주면 확인할 지점을 구체적으로 밝힌다.

중국어 간체·스페인어·독일어의 작성·교정에서는 [추가 언어 지침](expanded-languages.md)의 해당 언어 절을 읽는다.

## 여러 언어 버전 동기화

원문 버전과 변경 범위부터 확인한다. 사실·코드·지표·용어가 바뀐 부분과 그 영향을 받는 제목·요약·결론·표·링크를 함께 확인한다. 변경 요청이 좁으면 관련 없는 문체까지 다시 쓰지 않는다.

여러 파일을 관리한다면 기존 저장소의 언어별 경로·메타데이터 관례를 따른다. 동기화 상태를 기록할 때는 실제 확인한 원문 버전과 검토 범위를 쓰고, 확인하지 않은 다른 언어 버전을 최신이라고 표시하지 않는다. 번역 파일을 만들었다는 이유만으로 사이트 게시나 외부 문서 변경까지 수행하지 않는다.

## 두 번에 나누어 검토

1. **의미와 기술 정보:** 원문과 직접 대조해 주장·조건·불확실성·수치·코드·출처가 보존되는지 확인한다. 기계적인 토큰 대조는 누락 후보를 찾는 보조 수단이며 의미의 동등성을 증명하지 않는다.
2. **대상 언어의 글:** 원문을 문장별로 따라 읽지 않고 결과물만 읽어 지시 대상, 흐름, 용어와 말투가 자연스러운지 확인한다. 본문뿐 아니라 제목·소제목·표 머리글·캡션·출력 설명에 의도하지 않은 다른 언어가 남았는지도 살핀다. 공식 명칭·코드·실제 로그·의도한 원어 병기는 유지한다. 다시 다듬은 뒤에도 핵심 의미는 원문과 대조한다.

수치·코드·핵심 주장이 잘못 바뀌면 자연스러운 문장이더라도 수정 전에는 통과로 평가하지 않는다. 역번역만으로 정확성을 인정하지 않는다.

## AI 검토를 기본으로 운영하기

장문 번역·여러 언어 버전의 동기화는 별도 AI 세션을 사용할 수 있고 위임이 허용된 경우 [독립 AI 검토 절차](ai-review.md)로 확인한다. 의미 대조와 대상 언어 교정을 함께 검토하되, 한 검토자가 여러 언어를 다뤄도 된다. 사람의 검토는 요청이 있을 때 추가하며 기본 통과 조건으로 요구하지 않는다. 자체 AI 검토·별도 세션 AI 검토·사람의 검토를 구분하고 확보하지 않은 검토는 완료로 표시하지 않는다.
