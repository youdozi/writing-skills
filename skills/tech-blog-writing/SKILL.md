# 기술 블로그 글쓰기

독자가 기술적 맥락과 판단 근거를 이해하고 자신의 상황에 적용할 수 있는 글을 만든다. 사용자가 지정한 언어, 독자, 문체, 구성과 분량을 우선한다. 언어 선택은 아래 기준을 따른다.

## 간결하게 쓰기

새 글은 간결함을 기본으로 삼고, '심플하게', '짧게', '압축해 줘'라는 요청에는 핵심과 필요한 설명만 남긴다. 사용자가 상세한 설명이나 특정 분량·형식을 요청하면 그 범위를 충족한다.

- 첫 문단에서 핵심 답이나 결과를 밝힌다. 긴 배경 설명으로 시작하지 않고, 맥락은 그 답을 이해하는 데 필요한 위치에 짧게 붙인다.
- 한 글이 답할 질문을 좁히고, 결론을 뒷받침하는 근거·핵심 예제·적용 조건·필요한 다음 행동을 골라 담는다. 글 유형 표의 항목을 모두 별도 목차로 만들거나 관련 지식을 빠짐없이 설명하려 하지 않는다.
- 독자가 이미 아는 기초, 같은 뜻의 반복, 의미 없는 수식어, 결론을 바꾸지 않는 곁가지와 상투적인 도입·마무리를 먼저 삭제한다. 예제를 늘리기보다 핵심 예제로 설명이 끝나는지 확인한다.
- 문단은 하나의 논점에 집중하고 문장은 구체적인 주어와 동사로 쓴다. 긴 문장은 이해 단위로 나눈다. 압축할 때는 관찰과 그 적용 환경·조건을 함께 두고, 한계와 다음 행동을 문장 사이에 배치해 한 문장에 몰리지 않게 한다. 문장 수가 정해져 있어도 환경·조건을 빼거나 접속어로 원자료에 없는 시간 순서·인과관계를 만들지 않는다. 한 문장마다 줄을 바꾸거나 모든 내용을 목록으로 바꾸지 않는다. 짧은 글은 제목과 본문으로 바로 전달하고, 읽는 데 도움이 될 때만 소제목·표·요약을 붙인다.
- 삭제한 조건 때문에 결론이 달라지지 않는지 원문과 대조한다. 중요한 예외·부정·불확실성·측정 범위·출처와 실행에 필요한 코드는 남긴다. 짧아졌다는 이유만으로 정확해졌다고 평가하지 않는다. 요약을 요청하지 않은 번역에서는 원문의 정보 범위를 유지하며 표현을 간결하게 한다.
- 퇴고·압축 결과는 수정한 글을 먼저 제공한다. 요청하지 않은 제목 후보·작성 과정·수정 해설·반복 요약은 덧붙이지 않는다. 꼭 확인할 사실이나 의미가 바뀐 부분만 필요할 때 짧게 알린다.

## 언어와 작업 유형 선택하기

AI 도구의 사용법·프롬프트·업무 절차를 따라 하는 가이드는 사용 가능한 `ai-guide-writing`이 적합하다. API·실행 코드·개발 환경의 구현과 재현이 중심이면 이 스킬의 기술 튜토리얼 범위를 유지한다. 다른 스킬은 필수 의존성이 아니다.

- 완성된 글을 번역·현지화하거나 원문과 번역문을 대조하는 요청만 있으면, 사용 가능한 `translate` 스킬을 선택한다. 메모에서 다른 언어의 새 글을 구성하는 작업은 이 스킬로 수행한다. 새 글 작성 후 번역까지 요청하면 원문을 완성한 뒤 번역 단계에 `translate`를 사용한다. 해당 스킬이 없거나 사용자가 이 스킬을 명시한 경우에는 아래 다국어 지침으로 처리한다.

- 새 글 작성, 번역, 현지화, 대상 언어의 퇴고, 여러 언어 버전의 동기화를 구분한다. 번역 요청만으로 요약하거나 사실을 추가하지 않는다.
- 명시한 대상 언어를 우선한다. 기존 글의 퇴고·이어쓰기에서는 그 글의 언어를 유지하고, 언어를 지정하지 않은 새 글은 한국어로 작성한다. 대상 언어가 불명확한 번역 요청은 번역 방향을 확인한다. 언어만으로 지역이나 독자의 기술 수준을 추정하지 않는다.
- 한국어 이외 언어로 작성·퇴고하거나 번역·현지화·언어 버전 동기화를 수행할 때는 [다국어 작성 지침](references/multilingual.md)을 읽는다. 한국어 단독 글의 일반적인 작성·퇴고에는 추가 지침을 읽을 필요가 없다.
- 언어가 바뀌어도 주장·부정·조건·불확실성·측정 범위를 보존한다. 코드·수치·단위·버전·출처는 원문과 대조하고, 표현 수정과 사실 변경을 구분한다.

## 작업 범위 정하기

- 요청이 기획, 개요, 초안, 퇴고 중 어디에 해당하는지 판단하고 그 결과물을 제공한다. 개요 요청을 완성 글로 확대하지 않는다.
- 제공된 메모, 코드, 초안, 저장소 문서에서 주제, 예상 독자, 해결하려는 문제와 핵심 주장을 파악한다. 관련 자료만 확인한다.
- 정보가 부족해도 합리적인 기본값으로 진행할 수 있으면 짧게 가정을 밝히고 작업한다. 주제 자체나 핵심 사실이 없어 글을 구성할 수 없을 때만 필요한 질문을 묶어 묻는다.
- 기존 글을 다듬을 때는 저자의 관점과 말투를 보존한다. 표현 수정과 기술적 내용 변경을 구분하고, 근거 없이 결론을 바꾸지 않는다.

## 글의 중심 잡기

작성 전에 다음을 내부적으로 정리한다. 사용자가 기획을 요청한 경우에는 결과물에 드러낸다.

- **독자:** 무엇을 이미 알고 있으며 어디에서 막히는가.
- **읽을 이유:** 어떤 문제를 해결하거나 어떤 판단을 도울 것인가.
- **핵심 주장:** 읽은 뒤 기억하거나 실행할 한 가지는 무엇인가.
- **근거:** 코드, 관찰, 문서, 실험 중 무엇으로 주장을 뒷받침하는가.

주제가 넓으면 한 글에서 설명할 수 있는 질문으로 좁힌다. 제목은 실제 내용과 적용 범위를 드러내도록 쓰고, 근거 없는 최상급이나 과장된 성과를 넣지 않는다.

## 설명과 예제 설계하기

- 개념 해설에서는 독자가 이미 아는 내용에서 새로 이해해야 할 내용으로 연결한다. 제공된 질문이나 초안에서 혼동이 드러나면, 차이를 이해하는 것이 어떤 문제 해결이나 판단에 도움이 되는지 설명한다. 독자의 오해를 임의로 만들거나 독자를 탓하지 않는다.
- 예제는 핵심 동작을 드러내는 작은 사례에서 시작한다. 여러 예제를 사용할 때는 설명하려는 차이가 보이도록 변경 범위를 제한하고, 무엇이 달라졌으며 왜 결과가 바뀌는지 연결한다. 단순화한 가정과 생략한 동작을 밝히고, 설명용 계산을 실제 측정값처럼 제시하지 않는다.
- 쉬운 설명에서도 독자가 후속 자료를 찾는 데 필요한 기술 용어는 남기고 처음에 의미를 풀어 쓴다. 구체적인 구성·표현의 참고가 필요하면 [언어별 기술 글 분석](references/blog-patterns.md)에서 관련 유형만 확인한다. 특정 저자의 문체를 언어 전체의 규칙으로 만들지 않는다.
- 시각화는 사용자가 요청했거나 문장·코드만으로 이해하기 어려운 관계를 설명할 때 사용한다. 시간 순서는 타임라인·시퀀스, 상태 변화는 상태도, 변수에 따른 동작은 조작 가능한 예제를 고려한다. 주제·출력 형식·사용 가능한 도구에 맞춰 선택한다.

## 그림과 코드 전달하기

- 그림과 코드는 요청한 범위에서 이해·재현에 필요한 것을 각각 선택한다. 짧은 새 글이나 구현 변경이 없는 회고에 둘을 일률적으로 붙이지 않는다. 함께 사용해 같은 동작을 설명할 때는 본문·그림·코드의 입력, 단계, 분기, 상태 변화와 순서를 대조한다.
- 그림에는 대상 언어의 대체 텍스트와 필요한 짧은 설명을 제공한다. 확인 가능한 환경에서 실제 표시와 모바일 폭의 글자·화살표 가독성을 점검한다. 렌더링되지 않는 Mermaid 원문을 완성 그림으로 제시하지 않는다. 대상 환경이 지원하지 않으면 사용 가능한 도구로 SVG 등 표시 가능한 형태를 제공하고, 대상 게시 환경을 확인하지 못했다면 확인한 범위를 짧게 밝힌다. 원고 작성만으로 게시·배포하지 않는다.
- 코드가 필요하면 이해·재현에 필요한 실행 환경·입력·설정을 갖춘 최소 예제를 우선한다. 구현이 없는 글에 코드를 만들기 위해 구현이나 실행 이력을 창작하지 않는다. 설계 판단을 보여줄 필요가 있을 때는 설정·명령 또는 의사코드임을 밝힌 절차를 사용할 수 있다. 실제 실행 결과와 예상 결과, 생략한 부분을 구분한다.
- 개요·제목·최소 교정 등 좁은 요청과 사용자의 그림·코드 제외 지시를 우선한다. 완성 글의 번역은 원문의 그림·코드를 보존·현지화하고 원문에 없는 구현을 추가하지 않는다.

## 유형에 맞게 구성하기

아래 흐름은 출발점이다. 모든 글에 같은 목차를 강제하거나 해당 내용을 채우기 위해 사실을 만들지 않는다.

| 글 유형 | 권장 흐름 | 독자가 판단하는 데 필요한 정보 |
| --- | --- | --- |
| 튜토리얼 | 목표 → 준비 조건 → 구현 → 결과 확인 | 실행 환경, 필요한 코드와 설정, 성공 여부 확인 방법 |
| 개념 해설 | 구체적인 질문 → 동작 원리 → 예시 → 적용 범위 | 용어의 의미, 인과관계, 비유가 설명하지 못하는 부분 |
| 트러블슈팅 | 증상 → 확인한 증거 → 원인 → 해결 → 검증 | 재현 조건, 가설과 확인 결과, 해결이 유효한 조건 |
| 기술 비교 | 요구사항 → 비교 기준 → 관찰과 차이 → 선택 근거 | 버전과 환경, 대안별 비용, 선택이 달라지는 조건 |
| 프로젝트 회고 | 목표와 제약 → 주요 결정 → 결과 → 배운 점 | 당시의 맥락, 실제 결과, 다음에 바꿀 구체적 행동 |

도입에서는 문제와 핵심 답을 일찍 보여준다. 본문은 독자가 이해하는 순서로 전개하고, 작업 일지를 그대로 나열하지 않는다. 필요한 경우 결말에서 결과와 적용 조건을 정리하되, 짧은 글에는 이미 전달한 결론을 되풀이하지 않는다.

긴 글에서는 사전 지식과 핵심 질문을 일찍 밝혀 읽을 범위를 판단할 수 있게 한다. 필요한 경우 요약·목차·부록으로 핵심 흐름과 상세 설명을 나누고, 본문의 결론을 이해하는 데 필수적인 조건은 본문에 남긴다. 사용자 지정 구성과 분량을 우선하며, 모든 글에 이 요소를 붙이지 않는다.

설계·기술 선택 글에서는 먼저 만족해야 할 요구사항과 실패로 간주하는 상황을 밝힌다. 해결책이 그 조건을 어떻게 충족하는지 연결하고, 보장이 깨지는 가정이나 반례가 있으면 함께 설명한다. 제공되지 않은 요구사항은 저자의 실제 제약처럼 서술하지 않고 가정이나 제안으로 구분한다.

문제 해결·회고 글에서는 결론을 이해하는 데 필요한 실패한 가설과 시도를 보존한다. 각 가설을 지지하거나 배제한 관찰을 연결하고, 실제로 시도한 방법과 검토만 한 대안을 구분한다. 당시 알고 있던 정보와 사후에 확인한 사실, 임시 완화책·최종 개선·계획 중인 조치를 구별하고 각 선택이 남긴 비용을 설명한다. 실패했거나 검증하지 못한 방법을 일반적으로 무효인 해법으로 단정하지 않으며, 자료에 없는 시행착오나 판단 과정을 창작하지 않는다.

실무 적용이 목적인 글에서는 사례를 독자가 따라갈 수 있는 시작 조건, 첫 확인 방법, 결과에 따른 다음 행동으로 연결한다. 제공된 진단·도입 절차가 있으면 활용하고, 새로 제안한 절차는 제안임을 밝힌다. 자료에 없는 명령이나 판정 임계값을 검증된 방법처럼 추가하지 않는다. 개요·짧은 설명 등 요청한 범위 안에서 필요한 만큼만 다룬다.

## 기술적 근거 다루기

- 제공된 사실, 직접 확인한 사실, 해석이나 가설을 구분한다. 과거 기록의 모호한 표현과 현재 예제에서 새로 정한 정의를 구별하고, 현재 정의를 과거의 의도로 소급하지 않는다. 저자의 경험, 장애 이력, 팀의 의사결정, 인용문을 창작하지 않는다. 1인칭 경험 서술은 사용자가 제공한 경험에 한정한다.
- 최신 API 동작, 지원 버전, 가격처럼 바뀔 수 있는 정보가 주장에 필요하면 사용할 수 있는 검색·문서 도구로 공식 문서나 원문을 확인한다. 링크 내용을 확인하지 못했다면 확인한 것처럼 인용하지 않는다.
- 출처는 해당 주장을 뒷받침하는 위치에 연결한다. 원문을 길게 옮기기보다 글의 맥락에 맞게 설명한다. 외부 사례에 미완료 편집 메모나 확인되지 않은 경험 수치가 남아 있으면, 공식 게시물이라도 그 부분을 검증된 근거로 쓰지 않는다.
- 코드에는 이해나 재현에 필요한 import, 설정, 입력을 포함하되 글의 논점을 가리지 않게 한다. 생략한 부분과 의사코드는 명시한다. 자격 증명과 식별 가능한 내부 정보는 예시 값으로 바꾼다.
- 코드를 실행하거나 테스트하지 않았다면 검증했다고 쓰지 않는다. 실행 예시와 예상 출력은 실제 실행 결과와 구별한다. 코드 확인을 위해 필요한 범위를 넘어 환경을 변경하지 않는다.
- 성능 개선 수치는 측정 자료가 있을 때만 사용한다. 비교에는 환경, 입력, 측정 방법과 기준을 설명하고, 한 환경의 결과를 일반적 우열로 확장하지 않는다. 지표를 선택한 이유와 무엇을 뜻하는지 필요한 만큼 설명하며, 자료에 있는 표본 수·집계 구간·평균·백분위 등 해석에 중요한 조건을 보존한다. 단일 환경 실험과 운영 관측, 상관관계와 인과관계를 구분하고, 조건이나 지표가 다른 수치를 직접 비교하거나 측정하지 않은 지표의 개선으로 확대하지 않는다.
- 핵심 주장마다 이를 뒷받침하는 근거와 적용 조건을 대조한다. 관찰된 변화와 원인으로 입증된 효과를 구분하고, 함께 바뀐 설정·트래픽·데이터 등 다른 설명 가능성을 반영해 표현의 강도를 조절한다. 특정 환경의 선택을 일반적인 정답으로 확장한 문장은 조건을 붙이거나 범위를 줄인다. 이 대조는 내부 검토로 수행하고, 별도 리뷰를 요청받았거나 중요한 수정 이유를 설명할 때만 결과를 드러낸다.
- 개선되지 않은 지표와 부작용도 선택에 중요하면 보존한다. 개발 환경 결과를 운영 성과로, '통계적으로 유의한 차이를 확인하지 못함'을 '효과가 없음'으로 바꾸지 않는다. 제목·요약·결론에도 본문과 같은 측정 범위와 주장 강도를 적용한다.
- 중요한 근거가 비어 있으면 필요한 자료를 질문하거나 해당 주장과 정밀도를 줄인다. 사용자가 불완전한 초안을 원할 때는 `[확인 필요: 측정 환경]`처럼 채워야 할 내용을 구체적으로 표시한다.

## 문장과 설명 다듬기

초안을 쓴 뒤 문단의 흐름과 문장 표현을 한 차례 따로 다듬는다. 저자의 말투와 대상 언어의 자연스러운 어순을 유지한다.

- 문단마다 하나의 논점을 두고 주장에 이유나 예시를 연결한다. 앞 문장이 제기한 질문을 다음 문장이 이어받게 하며, 기술 용어 나열로 설명을 대신하지 않는다.
- 뜻이 같으면 직접적인 동사를 쓴다. 예를 들어 “설정 변경을 진행했다”는 “설정을 바꿨다”, “확인하는 것이 가능하다”는 “확인할 수 있다”로 다듬는다. 행위 주체를 알 때 능동형을 고려하되, 주체가 불명확한 원문에 행위자를 만들지 않는다.
- 긴 명사 연결과 겹친 수식어를 풀고, 주어와 서술어가 자연스럽게 호응하는지 확인한다. “이”, “해당”, “이를 통해”의 대상이 모호하면 필요한 명칭을 다시 쓴다. 문장을 잘게 끊어 흐름을 잃거나 문장마다 줄을 바꾸지는 않는다.
- “본 글에서는 살펴보고자 한다”, “현대 소프트웨어 개발에서”, “매우 중요하다” 대신 실제 답·동작·영향을 쓴다. 같은 답이나 주의가 도입·본문·결말에 반복되면 가장 필요한 위치에 남긴다. 새로운 정보가 없는 마무리는 생략할 수 있다.
- 접속어는 앞뒤 관계를 드러낼 때만 쓴다. “또한”, “따라서”, “한편”을 문단마다 붙이거나 원자료에 없는 인과·시간 순서를 만들지 않는다. 반복되는 종결어미를 피하려고 어색한 동의어를 돌려 쓰지 않는다.
- 조건·부정·가능성은 뜻을 바꾸는 정보다. “발생할 수 있다”를 “발생한다”로, “개발 환경에서 확인했다”를 일반적인 보장으로 바꾸지 않는다. 한계를 짧게 합치더라도 무엇을 확인하지 않았는지 남긴다.
- 독자가 검색할 기술 용어와 코드 식별자·공식 명칭은 보존한다. 처음에 필요한 만큼 뜻을 풀고 같은 개념은 같은 말로 쓴다. 비교의 장단점은 글의 요구사항에 연결한다.
- 표는 같은 기준의 비교에, 목록은 절차나 병렬 항목에 사용한다. 설명의 연결이 중요하면 문단으로 쓴다. 압축률보다 독자가 핵심과 조건을 한 번에 이해할 수 있는지를 기준으로 마무리한다.

## 전달 전 확인

요청한 범위에서 다음을 점검하고 필요한 부분을 고친다.

- 요청한 본문·단계·코드·출력을 제공했는가. 간결함 때문에 제목이나 요약만 남지 않았는가.
- 제목과 도입이 본문에서 실제로 답하는 질문을 약속하는가.
- 독자가 핵심 답을 일찍 찾을 수 있고, 의미와 재현성을 유지하면서 지울 수 있는 반복·배경·형식적 마무리가 남아 있지 않은가.
- 명사 연결·겹친 수식·불필요한 우회 표현을 다듬었으며, 주어·서술어와 문장 사이의 연결이 자연스러운가.
- 예상 독자가 기존 지식에서 새 개념으로 따라갈 수 있으며, 예제의 변화와 결과가 설명에 연결되는가.
- 핵심 주장의 강도가 근거와 맞으며, 관찰·인과관계·추정과 적용 조건이 구별되는가.
- 설계의 성공·실패 조건이 드러나고, 문제 해결·회고에서 가설의 근거와 당시의 정보·실행 여부·조치 상태가 구별되는가.
- 실무 적용 글에서 독자가 시작 조건과 첫 확인 방법, 결과에 따른 다음 행동을 알 수 있는가.
- 그림을 제공했다면 확인 가능한 환경의 표시·대체 텍스트·가독성을 점검했는가. 같은 동작을 설명하는 코드가 있다면 단계·분기·상태·순서가 일치하며, 확인하지 못한 환경을 검증했다고 쓰지 않았는가.
- 코드·명령·버전·출처가 본문의 설명과 일치하는가. 번역·현지화에서는 원문의 수치·조건·주장 강도도 유지되는가.
- 주장에 영향을 주는 미확인 정보나 실행하지 않은 검증이 드러나는가.

기본 결과물은 요청한 제목·개요·본문 또는 수정본 자체로 제공한다. 기획 메모, 체크리스트, 제목 후보를 매번 덧붙이지 않는다. 퇴고 시에는 수정본을 먼저 제공하고, 의미가 달라진 부분이나 남은 확인 사항만 필요에 따라 짧게 설명한다. 파일 저장을 요청했거나 저장소의 작성 관례가 있는 경우에는 해당 위치와 형식을 따른다. 글 작성 요청만으로 외부 게시나 배포를 수행하지 않는다.

## AI 검토 우선하기

검토는 AI를 기본으로 삼는다. 완성 초안·장문 번역·다국어 동기화에서 별도 AI 세션을 사용할 수 있고 위임이 허용돼 있으면 [독립 AI 검토](references/ai-review.md)를 우선 적용한다. 짧은 문장 수정은 자체 검토로 처리할 수 있다. 별도 세션을 사용할 수 없다면 자체 검토한 범위를 기록하며, 독립 검토라고 부르지 않는다. 사람의 검토는 사용자가 원할 때 추가하는 선택 사항이며 기본 완료 조건으로 요구하지 않는다.
