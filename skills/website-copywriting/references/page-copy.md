# 영역별 문구 선택

이 문서는 필요한 영역만 선택할 때 쓴다. 영역의 존재 자체를 완성도 기준으로 삼지 않는다.

## 첫 화면·소개

제목과 설명을 한 묶음으로 읽어 누가 무엇을 얻거나 찾을 수 있는지 확인한다. ‘더 나은 내일’ 같은 문장이 브랜드 자산이면 유지하면서 구체적 제공 내용을 옆에서 보완할 수 있다. 기능을 독자 이익으로 연결하되 ‘시간 절약 도구’를 근거 없는 ‘업무 시간 50% 절감’으로 바꾸지 않는다. 사진·영상이 주는 정보를 실제로 확인하지 않았다면 그것만으로 설명을 생략하지 않는다.

회사 소개는 확인된 활동·제공 범위·일하는 방식으로 신뢰를 만든다. 연혁·전문가 수·파트너·고객 사례가 없다고 가짜 항목을 채우지 않는다. 개인 포트폴리오에서는 팀 성과와 본인의 역할, 작업 시점·공개 가능한 결과를 구별한다.

## 서비스·과정·가격

서비스 설명은 대상의 일과 기능의 연결을 보여 준다. 이용 과정은 실제 순서와 이용자가 준비할 일을 드러내고, 폼 제출·상담·확정·결제·서비스 시작을 같은 단계처럼 쓰지 않는다.

요금은 단위와 실제 청구액을 함께 읽을 수 있게 쓴다. 월 환산액과 매월 청구, 연 결제와 월 결제를 구별한다. 부가세·최소 약정·좌석 단위·추가 요금·해지/환불·무료 범위 등 제공된 중요 조건은 해당 금액·행동 가까이에 둔다. 모르는 정책을 업계 관행으로 채우거나 비교표의 빈칸을 ‘제한 없음’으로 만들지 않는다. 제공되지 않은 ‘인기’, ‘추천’, 절감률을 사실 배지처럼 붙이지 않는다.

제공된 사례·후기는 실제 주장과 범위를 지킨다. 사용자가 승인하지 않은 실명·연락처·민감한 내용은 불필요하게 드러내지 않는다. 사례 하나의 성과를 전체 고객에게 보장하지 않는다. 증거가 없으면 검증 가능한 기능·과정으로 설명하고 빈 신뢰 영역은 뺄 수 있다.

## 행동 버튼·메뉴·FAQ

행동 문구는 다음 화면과 역할을 맞춘다. ‘가격 보기’와 ‘상담 요청’, ‘신청서 작성’과 ‘신청 완료’를 구별한다. 버튼이 여럿이면 같은 목적지·같은 동작에 일관된 이름을 사용하고 다른 목적지를 막연한 ‘더 보기’만으로 구분하지 않는다. 화면 위치·주변 문구가 제공되면 그 맥락을 함께 고려한다.

FAQ는 대상·준비물·제공 범위·가격·이용 순서처럼 결정에 필요한 실제 질문과 확인 가능한 답으로 구성한다. 정해지지 않은 정책의 답을 만들지 않는다. 본문의 슬로건을 질문형으로 되풀이하는 FAQ는 필요하지 않다. 답이 없는 질문을 반드시 넣어야 하면 원고 밖 확인 항목이나 요청한 자리표시자로 남긴다.

## 문의 폼·상태 문구

필요한 경우 필드 이름·짧은 작성 예시·보조 설명·전송 버튼·완료/오류 문구를 나누어 쓴다. 입력 안내만으로 라벨을 대신하지 않는다. 오류는 어떤 입력을 어떻게 고칠지 알려 주고 사용자를 비난하지 않는다. 작성 예시에는 실제 개인정보 대신 분명한 가상 값을 쓴다.

문의 접수 완료와 예약·계약·계정 생성 완료를 구별한다. 설계용 성공 문구는 해당 상태를 가정해 작성할 수 있다. 실제 화면의 문구는 확인된 시스템 상태와 맞추고, 초안 작성이 실제 접수·예약 완료를 뜻하는 것처럼 보고하지 않는다. 응답 시간을 받지 않았으면 ‘24시간 안에 연락’ 등을 보태지 않는다. 약관·개인정보 동의 문구는 실제 수집 항목·목적·보유 기간 등 운영 조건을 확인해야 하며 일반 카피로 적법성이나 완결성을 인증하지 않는다.
